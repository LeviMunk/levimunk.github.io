**Date:** 2026-11-18

## Goal

An actual signed-in owner can create a company, become its authorized Owner, reload or sign in again, and see only that company. The company has a stable ID and an explicit industry designation. CleaningOS may render tenant-specific business data only after server authorization.

A mere company-name field in localStorage, an unauthenticated `org_id` supplied by the browser, or a demo 'Connected' badge **must not** count.

## Precise core behavior

1. On the MunkOS application, an unauthenticated visitor cannot create or fetch a tenant. They are sent through the configured identity-provider sign-in.
2. After successful sign-in, the API validates the identity token server-side. No user-controlled email or client-supplied role is trusted as proof of identity.
3. The owner enters a business name and industry (first supported type: `cleaning`). The API validates and normalizes inputs, and assigns a **server-generated immutable tenant ID**.
4. The API creates the organization **and** its Owner membership **atomically** in the same database transaction. Failure rolls both back. No orphan tenant or membership.
5. It creates an onboarding progress record (e.g. `business_profile_started`) without inventing real domain/integration/payment statuses.
6. Repeating the same create request with the same idempotency key must return the existing tenant, not create a duplicate. New requests may create separate organizations only by an explicit supported multi-company flow.
7. A signed-in owner can list only their own organizations, select one they belong to, and retrieve its profile.
8. An unrelated authenticated user cannot read, list, update or join that tenant merely by knowing or guessing its ID.
9. Only server-authorized owners/admins can update a company profile or invite staff, with role checks and audit logging. Do not implement employee invites as Step 00.01 beyond defining the necessary boundaries.
10. After page refresh/sign-out/sign-in, company context comes back from authenticated server state, not browser-local company identity.
11. `cleaning` maps to the CleaningOS product descriptor without creating separate tenant types/databases per industry.
12. Emit an auditable `tenant.created` or `organization.created` event with actor, tenant ID, timestamp and idempotency key; do not send external notifications yet.

## Minimal API contract (adapt to existing MunkOS routes)

| Purpose | Method/route | Input | Result |
|---|---|---|---|
| Create authenticated company | `POST /organizations` | `name`, `industry: "cleaning"`, idempotency key | organization with canonical ID; owner membership created |
| List own companies | `GET /organizations` | authenticated user only | organizations accessible to caller |
| Read own company | `GET /organizations/:id` | ID in URL + authenticated user | 200 for member; 403/404 otherwise |
| Select company context | `POST /session/active-organization` (if needed) | authorized tenant ID | persisted server-side/session-validated selection |
| Update name/settings | `PATCH /organizations/:id` | authorized owner/admin, validated fields | updated scoped record |

If the existing MunkOS router already has equivalent endpoints, **use those names instead of introducing duplicate routes**. Existing schema names and roles take precedence over these sketches.

## Required integration boundary for CleaningOS

Future CleaningOS app launch must receive a validated signed-in identity and a server-confirmed active tenant, ideally via a shared MunkOS SDK/session endpoint:

```ts
type ActiveBusinessContext = {
  tenantId: string;
  industry: "cleaning" | string;
  displayName: string;
  membershipRole: "owner" | "admin" | "staff" | string;
  userId: string;
  verifiedAt: string; // generated by trusted server
}
```

No hardcoded tenant IDs; no frontend-authoritative roles. Keep a clearly separate **Demo Mode** that uses fictional browser-local data and cannot access production customer records. Add no fake login state inside CleaningOS.
